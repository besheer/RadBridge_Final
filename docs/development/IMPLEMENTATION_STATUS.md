# Architecture implementation and remaining gates

Date: 2026-10-16. Scope: isolated architecture port on `codex/radbridge-architecture-port`, published in draft PR #2 against GitHub `main`. The prior `refactor/development-foundation` branch remains unchanged. Production has not been modified. Clinical release metadata remains 5.46.9; these changes are not a deployed clinical release.

## Implemented ownership

- All 160 persisted models belong to 14 infrastructure model modules; the SQLAlchemy extension is unbound until application composition.
- All 949 extracted functions have executable owners in 32 component/route/helper modules. Eighty HTTP-dependent installers were assigned to web ownership without changing their handler bodies.
- All 76 migrated modules have one canonical owner and legacy aliases preserving module/exception/patch identity.
- The clinical application factory supports independently supplied database, secret, storage, cookie and runtime URL configuration. Two-instance authorization/scope tests cover supported isolation; provider and host flags remain process-level.
- Twenty-nine explicit workflow dependency boundaries are registered in `ris/application/port_contracts.json`. The architecture checker rejects infrastructure, web, framework and runtime imports in those services. Direct Flask imports are now rejected in the entire application/services package, including unregistered modules. This does not certify transitive dependencies or all old orchestration as clean.
- The legacy `Bindings.namespace()` compatibility view now exposes only names declared for that component; the dynamic notification-reset model is declared explicitly. This narrows old dynamic lookup, but the remaining `namespace()` call sites and broad compatibility bindings still need gradual replacement.

`ris/docs/CODE_MAP.md` links executable models, composed routes, canonical legacy owners and explicit port boundaries. Regenerate it using `python ris/tools/generate_code_map.py` after ownership changes. `application/component_manifest.json` and `application/module_manifest.json` remain the ownership inventories.

## Explicit workflow boundaries

| Area | Implemented dependency separation | Remaining work |
|---|---|---|
| Assignment | Scoped queries, capacity/count policy, pure ranking/deadlines, case mutations/offer acceptance, grouped visit workflows, read-only monitoring projections | Aggregate visibility/performance review, coordinator previews, evidence gathering, broader workers and callbacks still compose at the compatibility edge |
| Registration | Patient field/date/sex policy, visit selection and reserved assignment, latest-decision insurance readiness, structured demographic request/review, existing-patient appointment creation | Patient creation, remaining scheduling/booking/check-in/rescheduling transactions, concurrent demographic request serialization, approved identity-change execution and external RIS interfaces |
| Readiness | Exception/history/alias/override mutations, scoped RIS candidate search, bounded scheduling/refresh, read-only operations aggregation | Actual evidence acquisition/evaluation, broader exceptions and operational worker lifecycle |
| Identity | Pure scope policy, explicit qualification/scope evidence and request/ORM guard ownership | Broader user lifecycle/import transactions, permission catalogue lifecycle and host security/VPN integration |
| Reporting | Immutable report saving with repository/artifact ports, edit leases, correction request/review; correction center routes audited with order-based branch checks on search, submit, review and execution | Reference resolution, correction/editor finalization, callbacks, exports and external editor failure acceptance |
| Finance | FINAL replacement entitlement settlement, branch collection checks, net receipt/refund evidence, authorized daily closing SAVE/CLOSE, manual report/image delivery readiness | Broader receipts/disbursements/refunds, delivery event write transactions, finance unit-of-work/error presentation and external accounting integration |
| Inventory | Original-lot return policy, repository and movement dependencies | Consumption, general stock movement, warehouse lifecycle and stock transport interfaces |
| Clinical staff/RT | Owned models, pure RT input validation, manual course/PET-link/external-plan/session/support/read ports and returned-document prerequisite read ports; components and web routes | staff mutation/worklist transactions, RT permissions/configuration and external acceptance; no treatment-device integration or controller is supplied |
| Imaging/viewers | Owned identity/matching policies, imaging adapters/routes and viewer extension; DICOM connection branch authorization receives the request user and global-access decision explicitly | Provisioned synthetic PACS/viewer acceptance, partial transport/retry/recovery contracts |
| Communications/operations | Owned adapter/extension/component modules | Narrow external-provider dependencies, operational recovery and storage/worker lifecycle |

Detailed decisions are in ADRs 001–051. Canonical ownership, explicit use-case inversion and real external integration are separate claims. A screen, a source assertion or a renamed module alone does not establish working integration.

## Preserved contracts and focused evidence

Before/after runtime captures retain the same 160 tables and 546 URL registrations, including types/defaults, foreign keys, indexes, constraints, methods and endpoints. No schema migration or data transformation was introduced. Handler-source and facade-identity tests remain active.

Focused runtime suites retain branch/role scope, receiving assignment barriers, immutable VERIFIED/FINAL reports, scoped editor leases, correction review and FINAL-only replacement settlement. Readiness aliasing requires captured PACS evidence; image exceptions cannot invent images; failed PACS evidence stays BLOCKED. Scheduling tests include PostgreSQL advisory-lock contention on two actual connections. Read-only receiving projections do not overwrite stored readiness.

Inventory returns preserve original lots, costs and expiry; prior disbursements are retained during replacement entitlement adjustments. Closing totals use receipt/refund accounting timestamps, original payment method buckets and finite decimal values. Daily closing authorizes before persistence, locks branch before closing, recomputes expected evidence under the locked context, rejects CLOSED mutations and audits flushed snapshots. Callers own commit/rollback except the explicitly documented per-case scheduler transaction boundary.

The Case Operations Control Center now derives branch scope from the signed-in user's registration policy. Its cases, leases, PACS inbox items, exam links, escalations and PACS events are restricted to the scoped order IDs; branch-specific strategies include only global and permitted-branch entries. The unassigned-case queue now filters cases, filter choices, branches and doctors to the user's branch, and both GET and POST assignment entry points share the existing assignment-role and branch guard. Synthetic SQL-backed and route tests cover permitted and empty scopes plus direct cross-branch read and assignment attempts. These fixes close those screens' direct cross-branch paths; they do not certify branch/role scope across the rest of the application or replace role-based browser UAT.

The readiness dashboard and exception resolver apply registration branch scope. Their queues, RIS results, filter choices and selected cases are restricted to permitted branches; cross-branch filters and selected cases are denied. The existing readiness check and exception history, series mapping and image-minimum actions verify scope before changing evidence. The same request-level query guard covers universal and advanced search, reports and CSV exports, receivables and receivables CSV, executive analytics and its doctor/device filters, operations command center, escalation board, command-center snapshots/events and the main dashboard, order and patient lists, appointments, operations dashboard/journey and management summary. Command-center audit/outbox events are matched to permitted order IDs. Direct case reads also check order details, order actions/labels/stickers, study thumbnails, patient documents, alerts, external priors, communications and timelines, attachment downloads/previews/deletion, MWL resend, and PACS case send/tracking views before loading or changing the object. PACS reconciliation, DICOM correction preview/commit, audit, exam-link create/remove, transfer retry/cancel and destination echo now use the same branch scope. Direct order, exam-link, transfer-job and destination IDs are validated before ORM identity-map lookups; branch-limited users cannot invoke the global auto-safe matcher or shared transfer processor. Shared global DICOM destinations remain available to branch users, while destinations assigned to another branch are denied. Unlinked PACS inbox studies are hidden from branch scope until they have a permitted order association, so manual matching of unlinked cases remains a central workflow. A focused SQL-backed test confirms permitted retry/cancel and global-destination echo actions succeed, foreign-branch jobs/destinations remain unchanged, and global queue processing is denied. Synthetic HTTP tests exercise allowed and cross-branch reads and mutations. This closes these routes' direct paths only; the wider auxiliary-query audit and role-based browser UAT remain open.

The assignment monitor and coordinator queue now restrict cases, offers, doctor lists, profiles and availability to the user's permitted branches. Manual assignment rejects foreign-branch doctors; offer start and expiry actions are branch-scoped; TAT reads share the branch guard. Assignment-offer policy and doctor-profile writes require management permission, and communication channel/template changes require `users.manage` or global access. The branch guard now receives the current user through composition instead of resolving the legacy global runtime. Synthetic tests for assignment monitoring (10), coordinator assignment (30), offer branch access (5), readiness/TAT scope (14), offer-policy permissions (2), communication permissions (2) and component boundaries (5) passed in separate local runs. These focused results do not replace full-suite CI or browser acceptance.

Daily closing policy and its payment-total repository now receive the composed runtime explicitly from the registered route/component bindings; that extension no longer calls `legacy_runtime.resolve_runtime`. Report/image delivery readiness likewise receives the runtime explicitly from registration route bindings. Focused close-governance, delivery and finance dependency suites pass, including a regression test for explicit daily-closing dependencies. These changes narrow two boundaries only; they do not establish independence of the wider finance module or PACS adapter.

Inventory consumption's order-lock adapter and the original-lot return adapter now receive runtime bindings explicitly from their component composition. Neither inventory adapter resolves the global runtime on these paths. A regression test forbids runtime resolution while synthetic stock is consumed and returned; inventory safety, return-service and component-boundary suites pass (32 tests). This does not separate the broader inventory lifecycle or reconcile legacy global stock balances.

Structured demographic-correction requests, review validation and stale-preview evaluation now receive runtime dependencies from their route bindings; the compatibility policy no longer resolves the application runtime itself. Request/review branch checks and four-eyes behavior remain covered by the synthetic correction workflow tests. This does not change patient identity automatically or complete the wider registration transaction boundary.

Insurance approval actor checks, readiness reads during work-order conversion and the outbound DICOM Worklist safety gate now receive runtime from route/component composition. The insurance adapter no longer resolves the global runtime; a synthetic regression test blocks any such lookup. This changes only dependency composition and preserves the approval rules and outbound block.

Reception collection authorization and branch guards now receive runtime from their permission, route and registration component bindings. The compatibility adapter no longer uses the global runtime resolver; a regression test forbids global lookup while evaluating reception permission and collecting a synthetic same-branch payment. Collection route and component-boundary tests pass (34 tests); this does not separate all finance workflows.

The legacy `/orders/new` POST is also guarded even though its GET redirects into the calendar workflow. Submitted branch IDs are checked from query or form data, and its legacy `patient` form field is explicitly checked against visible patients before the handler's `Query.get_or_404` lookup. Synthetic HTTP regression checks reject both a forged cross-branch registration target and a patient belonging only to another branch. This closes that endpoint's direct scope bypass; it does not make the legacy registration workflow a supported replacement for the calendar workflow.

Branch-limited user managers now see only accounts assigned to their permitted branches. Account edit, disable, password-reset and clinical-scope routes validate the target user before legacy identity-map lookups; creation and reassignment cannot place an account into the global/unassigned scope. Clinical-scope device choices are limited to the manager's branch. Synthetic HTTP tests cover hidden foreign/unassigned accounts and denied cross-branch mutations. Global role administration remains separately governed by role permissions and the delegated role hierarchy.

Finance workspaces now use the same branch guard: financial-center reports/exports, accounting reports/CSV, ledger entries/voids, and cashier listings. The shared ORM criteria also scopes branch-owned records directly through `branch_id`, covering financial entries that have no order or patient foreign key; filter choices for branch-owned users/devices are constrained as well. Synthetic cross-branch tests verify that finance reports, exports, and ledger pages exclude other-branch data, reject forged branch filters and block an entry submitted to another branch. This does not replace action-specific collection/financial permissions or certify every finance mutation path. A known gap remains in the legacy stock projection: `Consumable.stock_qty` is global, while newer batches/warehouses are branch-owned. The finance balance-sheet and inventory report must not be treated as branch-accurate until that stock accounting is reconciled.

Technician and nursing worklists/case pages, order consumable pages, inventory warehouse/stock/policy/ledger/consumption workspaces, and legacy batch/movement lists apply branch scope. Selected warehouses are validated against permitted branches, and ORM criteria bind warehouse-owned lots, policies, movements and usages to permitted warehouse IDs. Branch-scoped inventory users cannot invoke global warehouse bootstrap or legacy catalog migration, and warehouse/batch creation requires an explicit permitted branch. Synthetic SQL-backed tests cover cross-branch warehouse selection, reads, stock writes, staff case reads and global setup actions. Existing technician transition actions retain their dedicated `scoped_order`/workflow guards. Stock transfers now follow the approved central-only policy in ADR-040: branch users request from an active assigned central `MAIN` warehouse, central users alone approve/reject/dispatch, and only the destination branch receives; request, detail, actions, related lines and selectable warehouses are guarded. Synthetic route tests cover valid and invalid warehouse relationships and cross-branch denial. The legacy `Consumable.stock_qty` store remains global, so older balance-sheet and inventory projections are not branch-accurate until reconciled.

Smart-intake queues and session/document endpoints now restrict unlinked sessions to creators in the user's permitted branch set, while sessions linked or matched to a patient are visible only when that patient has a permitted-branch case. Child documents and field reviews inherit the session scope. The old standalone `/patients/new` POST is blocked for branch-scoped users because it can create an unassigned patient; branch users must use the unified registration transaction that binds the new patient to a branch visit. Synthetic route tests verify same-branch access and reject cross-branch session, document and legacy patient-creation attempts.

Patient data-management counts and single-patient preview/export/anonymize/delete routes now apply patient branch scope. Global manifest/all-patient backup and delete endpoints are rejected for branch-scoped users, even if a custom role grants those permissions. Synthetic tests verify cross-branch patient export cannot produce an archive, destructive per-patient actions are denied, and global all-patient operations are denied without changing the other branch's record.

## Release gates still open

1. Continue replacing `Bindings`, `legacy_runtime` and mixed extension callbacks with narrow evidence/repository/policy interfaces. Broad handler composition, cash entries, stock consumption, registration booking, clinical staff/RT and provider/worker lifecycles remain unfinished.
2. Continue auditing branch/role visibility of auxiliary queries and operations metrics; the case-readiness and exception routes have been closed and covered with synthetic HTTP tests. Run role-based browser UAT with synthetic cases.
3. Provision synthetic PACS/OHIF/ONLYOFFICE failure acceptance: delayed/lost callbacks, reassignment, partial transfer, retry uncertainty, queue restart and destination storage confirmation. Screens/source checks do not replace these scenarios.
4. Validate upgrade/rollback and operational recovery in an isolated environment. PR review, merge and production deployment require a separate release decision.

Module/port counts are concrete inventory measures, not a percentage of total architecture completion or clinical deployment readiness. No live patient data, production database snapshot, credentials or host secrets are added by this development work.
