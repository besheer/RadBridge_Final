# جاهزية الفصل والنقل إلى سيرفر آخر

تاريخ المراجعة: 2026-10-14. النطاق: فرع `codex/radbridge-architecture-port` وPR #2، commit `c3c67f908687288eda19586e3f1af28d5114f190`. لا يتضمن هذا المستند نقلًا أو نشرًا أو تعديلًا للإنتاج.

## الحكم الحالي

يمكن تجهيز نسخة RIS/PostgreSQL للتجربة على سيرفر Ubuntu منفصل باستخدام إعداد التطوير الموجود. لا توجد أدلة كافية لاعتماد نقل النظام الكامل للإنتاج الآن. استقلال الكود عن جهاز التطوير لا يساوي اكتمال حزمة التشغيل أو نقل بيانات التشغيل.

`compose.dev.yaml` و`development/Dockerfile` مخصصان لقاعدة جديدة وبيانات تطوير. `development/initialize.py` مقيد بقاعدة Compose المحلية ولا يصلح migrator لقاعدة إنتاج قائمة. لا تستخدمه بعد استعادة قاعدة فعلية.

## فصل التبعيات

- ملكية 949 دالة مكتملة في الجرد، والجداول والمسارات محفوظة؛ لا يعني ذلك فصل جميع التبعيات.
- أصبح سجل `application/port_contracts.json` يتضمن 29 خدمة، ويشمل الآن إنشاء حجز لمريض موجود، بجانب تصحيح البيانات وجاهزية التسليم ومتابعة التوزيع.
- خدمات السجل تخضع لفحص يمنع imports للبنية التحتية والويب والإطار وlegacy_runtime. وحدات domain مقيدة بالمكتبة القياسية وسياسات domain.
- ما زال `app.py` يركب المكونات باستخدام Bindings. جرد ساكن بعد الفصل سجل 6621 مرجع تبعية معلنًا للدوال الأصلية، وأقصى دالة لها 46 اسم تبعية. هذه مراجع أسماء، وليست عدد خدمات أو عيوبًا أو مقياسًا لنسبة الإنجاز.
- الجرد الساكن الحالي سجل 27 موضع import لـ`application.legacy_runtime` في 11 ملفًا، و11 استدعاء `namespace()`. فُصلت سياسة الإقفال اليومي ومجاميع التحصيل وجاهزية تسليم التقارير/الصور وطلبات تصحيح بيانات المريض ومراجعتها بحيث تستقبل runtime المعلن صراحة من نقطة التركيب بدل استدعاء resolver داخلي. بعض مواضع runtime الأخرى تخص حافة التركيب/factory، والباقي يحتاج تصنيفًا قبل تغييره. هذه الأعداد ليست نسبة إنجاز.
- ما زالت أعمال فصل في الحجز والتحصيل/صرف النقد واستهلاك المخزون وworkers وأدلة الجاهزية والمحرّر ودورة المستخدم وإعدادات المزودين.
- أداة `tools/audit_dependency_seams.py` تضيف جرد imports للإطار والويب والبنية التحتية داخل application/services، حتى خارج سجل ports. بعد نقل ستة مالكين لـHTTP إلى web، لا توجد imports مباشرة لـFlask في application/services ويمنعها فحص شامل. نُقل تركيب فحص مستندات الحالات المعادة إلى نقطة تركيب `app.py` مع callback من runtime، كما نُقلت شروط استعلام كيو الفني وبحث قائمة الإسناد المجمع إلى محوّلات تحت infrastructure. أصبح عدد imports المباشرة لـFlask/SQLAlchemy/web/requests داخل الخدمات صفرًا في الجرد الساكن. لكن خدمات مثل الإسناد المجمع ما زالت تستخدم ORM عبر runtime (`m.Order.query` و`m.db`)؛ صفر imports مباشر لا يعني فصل التبعيات أو الاستعلامات كاملة. لم تُفصل معاملات CSV أو تنفيذ الفحص أو المحرّر؛ هذه ما زالت تحتاج ports ومراجعة.

طلب تصحيح البيانات أصبح خدمة ذات repository/policy/actor/clock/audit صريحة. الطلب والمراجعة لا يصححان هوية المريض أو دراسة PACS تلقائيًا. صلاحيات المسارات منفصلة، ومعاملات commit/rollback لدى المستدعي. راجع ADR 034.

## حزمة التشغيل: ما الموجود وما يحتاج تجهيزًا

| العنصر | الحالة والأثر على النقل |
|---|---|
| كود RIS والتبعيات المقيدة | موجود؛ CI للـcommit `c3c67f9` نجح، لكن يلزم قبول Staging وتجارب استعادة مستقلة |
| إنشاء تطبيق بإعدادات مستقلة | موجود ومختبر بقاعدتين وإعدادات جلسات وتخزين منفصلة؛ بعض إعدادات providers/host ما زالت process-level |
| RIS/PostgreSQL development Compose | موجود؛ Docker smoke نجح على Ubuntu في CI للـcommit الحالي، وليس اختبار نشر إنتاج |
| PACS/Orthanc وبيانات الصور | غير ضمن Compose التطوير؛ يحتاج وجهة/خدمة وشبكة وتخزين وسياسة نقل منفصلة |
| ONLYOFFICE | غير ضمن Compose التطوير؛ يلزم إعداد عناوين داخلية/عامة وJWT ومسارات callback واختبار حفظ فعلي |
| OHIF وWeasis | ملفات التكامل ليست وحدها حزمة قبول؛ يلزم الأصول/الخدمة الملائمة وعميل Weasis واختبار المتصفح |
| قاعدة بيانات التشغيل | لا توجد نسخة إنتاج ضمن المصدر؛ نوعها ونسختها وحجمها ومسار الترقية يجب التحقق منها قبل النقل |
| التقارير والمرفقات والقوالب التشغيلية | الملفات الفعلية منفصلة عن الكود؛ جرد ومسارات وصلاحيات وhashes وربطها بالقاعدة مطلوبة |
| TLS وreverse proxy وDNS | إعدادات السيرفر الجديد تحتاج تجهيزًا واختبار روابط وتوجيه callbacks |
| workers والمهام المجدولة | يلزم جرد أوامرها وإعداداتها وownership ومنع تشغيل عاملين يكتبان نفس الكيو أثناء الانتقال |
| Fail2ban/geo policy/WireGuard | إعدادات مضيف وشبكات خارج حزمة الويب؛ يجب نقل السياسة بصورة مستقلة مع اختبار الوصول |
| الاستعادة وrollback | لم يثبت اختبار استعادة كامل على سيرفر جديد ضمن CI الحالي |

تحويلات المخزون تشمل الآن سياسة الفرع-إلى-المركزي: طلب الفرع من مخزن `MAIN` مرتبط ومصرح به، اعتماد/رفض/صرف مركزي فقط، واستلام للفرع الهدف فقط. اجتاز التنفيذ اختبارات صناعية آلية؛ قبول المستخدم بالمتصفح واختبار ظروف التشغيل على بيئة مستقلة لم يُنفذا بعد. الرصيد القديم `Consumable.stock_qty` ما زال مشتركًا ولا يصلح وحده لتقارير مخزون دقيقة حسب الفرع.

عناوين Orthanc الافتراضية في Compose هي `127.0.0.1` داخل حاوية RIS؛ هي ليست عنوان PACS على المضيف أو على سيرفر آخر. تعمد البيئة الحالية عدم توفير PACS. يلزم تكوين العنوان الداخلي المناسب قبل تجربة الصور، لا الاكتفاء بفتح صفحة login.

## بوابات قبول قبل النقل الكامل

1. تثبيت commit، وفحص حزمة المصدر والأصول والملفات المستبعدة. لا تنسخ أسرار التشغيل في Git أو صورة Docker.
2. تجهيز Ubuntu/Docker Compose وDNS/TLS والشبكات والمجلدات المستمرة. استخدم إعدادات جديدة مخزنة خارج Git.
3. اختبار RIS/PostgreSQL في بيئة صناعية. لا يعتبر نجاح login إثباتًا للحفظ أو الصلاحيات أو التكامل.
4. توفير PACS/editor/viewer صناعية: مطابقة الهوية، receiving/BLOCKED، وصول الطبيب، حفظ draft وFINAL والتصحيح، وtimeouts/retries/restarts.
5. اختبار كل دور وروابط مباشرة وتصدير وعدادات بين فرعين. راجع خصوصًا الاستعلامات المساعدة ذات النطاق القديم.
6. اختبار backup ثم restore لقاعدة وملفات صناعية مرتبطة، وفشل المعاملة بين DB وملف التقرير، ومهام الكيو الجزئية.
7. قبل نقل بيانات تشغيل فعلية: جرد read-only، واختيار snapshot متسق وآلية نقل الملفات والصور والتحقق منها، وخطة cutover/rollback وصلاحية اعتماد مستقلة. لم تُنفذ هذه المرحلة هنا.
